    How the quality system is built

    Most checks run at the fast layers. Only the revenue-critical guest journeys run end to end, and the release gate is tied to those journeys, not to a raw test count.

    ProductionSynthetic bookings and alerts on the booking path after deploy.
    P1 guest journeysPlaywright on desktop Chrome and a Pixel 7 profile; axe accessibility checks. Detox and Appium for native React Native (reference design).
    ContractJSON Schema on REST responses, GraphQL parity with REST, no full card numbers ever returned.
    APISearch, quote and booking, including payment approve, decline and outage paths.
    UnitPricing, cabin multipliers, promotion rules, input limits. Runs in under a second.

    Release gate policy

    • Any failing or untested P1 guest journey blocks.
    • A failing P2 requirement blocks unless it has a written exception with owner and expiry.
    • Pass rate must be at least 98%; at most 2 flaky tests; E2E under 10 minutes.

    AI with guardrails

    • Claude drafts test cases from acceptance criteria; each is schema-checked, de-duplicated and run against the service before a human reviews it.
    • Failures are clustered by signature; Claude proposes a root cause and next step.
    • Risk-based selection runs only the tests a change can affect.
